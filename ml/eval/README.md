# Оценка на роликах (ml/eval)

Все цифры - на роликах команды и открытых роликах, не с площадки. Это не оценка качества на объекте.

`eval.evaluate`
поддерживает `--json-out report.json`: P/R/F1 с учётом лишних дублей,
доля дублей, количество задержек, p50/p95 до события воркера (не до UI).
Сопоставление эпизодов теперь один-к-одному; старые отчёты перед сравнением
новых моделей нужно пересчитать. Для разных людей в одном окне времени
нужна разметка идентичности; только совпадения camera/type/time недостаточно.

Инструменты (из папки `ml/`):
- `py -m eval.videos fetch` - скачать ролики по `videos.md`, сверить SHA256;
- `py -m eval.evaluate events.json labels.json` - найдено/пропущено/ложные по всем типам;
- `py -m eval.patterns events.json labels.json --negative <ролик без нарушения> ...` - найдено, пропущено,
  ложные, дубли по каждому новому паттерну и отдельно ложные на роликах без нарушения; печатает таблицу ниже.

## Синтетический склад NVIDIA (P69): сближение, бег, зоны, дубли

**Синтетика, не съёмка.** Набор `nvidia/PhysicalAI-SmartSpaces` (Hugging Face, CC BY 4.0, без входа), сцена
`MTMC_Tracking_2025/val/Warehouse_015`, камеры `Camera`, `Camera_01`, `Camera_02` = `nvidia-w015-cam00/01/02`
(1920x1080, 30 к/с, по 5 минут, всего 0.25 ч). Ссылки и SHA256 - `videos.md` (ролики вне git, `py -m eval.videos fetch`, около 670 МБ).
Люди и техника - рендер Omniverse: картинка чище и однообразнее настоящих камер, цифры ниже к площадке не относятся.

Метки считает `py -m eval.nvidia_sim build` по эталону (`ground_truth.json`: 3D-положение, размер, поворот, рамки по камерам;
`calibration.json`: `cameraMatrix`, метры -> пиксели), не по нашей модели. Метр - мировые метры сцены.
| тип | как размечено |
|---|---|
| `vehicle_proximity` | зазор от ног человека до прямоугольника техники (погрузчик, паллетная тележка, AMR) на полу < 1.0 м не меньше 1 с, оба видны в камере |
| `running` | скорость человека >= 1.5 м/с за окно 1 с, не меньше 1 с. **Настоящего бега в сцене нет**: максимум около 1.8 м/с, порог взят на быстром шаге; строка проверяет измерение скорости, не бег |
| `danger_zone` | ноги в квадрате 4x4 м (зона `danger`) в месте, где проходит больше всего людей |
| `fence_crossing` | ноги в полосе 5x0.4 м (зона `fence`) поперёк самого частого движения; только Camera (в других камерах полоса не видна) |
Зоны - `zones/nvidia-w015-cam0N.json`, мировой полигон на полу спроецирован в кадр и обрезан по 0..1; для `running` добавлена зона `machinery` на весь кадр.
Меток: cam00 - 59, cam01 - 41, cam02 - 15 (`labels.json`). Перекрывающиеся метки разных людей склеены в одну.

Прогон: `py -m eval.run detect --device gpu nvidia-w015-cam00.mp4 nvidia-w015-cam01.mp4 nvidia-w015-cam02.mp4` (yolo11n + `ppe-v1`, 6 мин на GPU),
`py -m eval.run report --only nvidia-w015` (правила `worker/rules.yaml` без изменений, допуск 1 с):

| тип (синтетика) | найдено | пропущено | ложные | дубли | ложные на час видео | задержка ср / макс, с |
|---|---|---|---|---|---|---|
| `vehicle_proximity` | 18 | 21 | 42 | 74 | 168 | 1.2 / 5.7 |
| `running` | 20 | 31 | 70 | 4 | 280 | 0.7 / 1.9 |
| `danger_zone` | 9 | 1 | 1 | 190 | 4 | 4.0 / 12.2 |
| `fence_crossing` | 9 | 6 | 25 | 16 | 100 | 0.8 / 6.4 |

Ролика без нарушений в этой сцене нет (в каждой камере есть метки), поэтому «ложные на час» = ложные событий типа / 0.25 ч видео, а не по чистым роликам.
Выводы: дубли огромны у `danger_zone` (190 событий на 10 меток: один человек в зоне даёт много событий, метка склеена) и у `vehicle_proximity`;
сближение зависит от детекции погрузчика обычной моделью COCO на рендере; `running` ложных много, потому что порог правила (1.5 высоты человека в с)
не равен нашему 1.5 м/с и в кадре быстрый шаг похож на бег. Порогов не меняли.

## Сценарии на роликах (K20)

Ролики — K12 (`videos.md`, разметка `labels.json`, файлы в `demo/videos/`, вне git). Роликов S8 (каска, респиратор,
курение, зона) в `demo/videos/` пока нет: в разметке нет типов `no_helmet`, `no_respirator`, `smoking`,
`danger_zone`, как появятся — положить файл и интервалы, оценка подхватит сама.

### Запуск (из папки `ml/`)
```
py -m eval.run detect            # детекции роликов в кэш runs/eval-cache (модель людей + ppe-v1), один раз
py -m eval.run report            # найдено / пропущено / ложные / дубли по типам, пороги из worker/rules.yaml
py -m eval.run report --rules другой.yaml
py -m eval.run sweep running.speed_threshold=1,1.5,2 fall.transition_s=1,2   # перебор порога одного правила
```
Правила гоняются по кэшу с временем кадра (`find_violations` + `Debouncer` + `OverlapDeduper`), поэтому подбор порогов
не требует инференса. `detect` по умолчанию на CPU (`--device cpu`).

Как считается: ролик без записей в разметке — ролик без нарушений, любое его событие ложное (в том числе
`pixabay-26239`, `mixkit-20770`, `mixkit-24127`, `mixkit-45848`). Допуск по времени 1 с. Дубль — второе и
следующие события того же типа внутри одной размеченной метки. Зоны на роликах не размечены: для
`machinery`, `two_person`, `crowd_limit` берётся зона на весь кадр; правила `danger_zone`, `fence_crossing`,
`at_height`, `under_load` молчат. `no_helmet`, `no_respirator`, `smoking`, `lone_worker`, `overcrowding`
работают только на роликах, где в разметке есть их тип (иначе «ложные» были бы людьми без каски в бытовых
роликах и одиночками в кадре, которых никто не размечал).

### Что выбрано и почему (`worker/rules.yaml`)
| параметр | было | стало | почему |
|---|---|---|---|
| `fall.upright_ratio`, `fall.lying_ratio` | 0.8, 1.2 | 0.5, 0.7 | `shape()` считает отношение сторон в долях кадра, а не в физических; для кадра 16:9 «физические» 0.8/1.2 равны примерно 0.45/0.67. Проверено перебором: по сетке 0.4-0.6 x 0.7-1.0 падения находятся 2-5 из 5, при 0.5/0.7 все 5. Значения — пересчёт физического порога, а не подгонка под ролики. Лучше исправить правило (учесть `frame_aspect`) |
| `fall.min_ratio_change` | 2.0 | 1.5 | 2.0 -> 2 из 5, 1.5 -> 5 из 5, 1.2 -> 5 из 5 и 1 ложное; взято значение до первого ложного |
| `fall.transition_s` | 1.0 | 2.0 | 1-3 с дают одно и то же; падение с опорой занимает до пары секунд |
| `immobile.lying_ratio` | 1.2 | 0.7 | та же причина, что у падения |
| `immobile.duration_s` | 10 | 5 | 3 с и меньше дают ложные (1 с -> 9 ложных, 2 с -> 4), 4-5 с чисто; взято 5 как консервативное. Ролики с падением короче 5 с лежания, поэтому пропущено 3: метки неподвижности в черновике 2-5 с |
| `phone.min_frames` | 5 | 10 | при 5 кадрах дубли от двойной рамки человека; 10 кадров (~0.4 с) снимают часть, остальное убирает `OverlapDeduper` |
| `vehicle_proximity.min_frames` | 5 | 10 | ложные 5 -> 3 |
| `running.speed_threshold` | 1.5 | 1.5 | не менял: ниже 1.0 десятки ложных (0.4 -> 21, 0.2 -> 42), выше 2.0 ни одного бега. Бегущих в роликах K12 не находит ни один порог: камера ведёт за бегуном, смещение рамки мало |
| `lone_worker.duration_s`, `overcrowding.*` | 30 / 10, 5 | 30 / 10, 5 | не менял: ролики 10-15 с короче порога. При 5 с lone_worker находит 2 из 3 без ложных, при 3 с — 3 из 3, но это порог не для площадки. `overcrowding` не срабатывает ни при каких `max_people` 3-7 и `duration_s` 1-5: счёт людей в кадре мигает, а правило требует непрерывности |

Новый код: `worker/dedup.py` (`OverlapDeduper`) — один человек, которого вели два трека, даёт одно событие
(событие того же типа с IoU рамок >= 0.5 за 10 с отбрасывается); включён в `run_camera`. Без него дубль был
на `mixkit-41638` (две рамки на один и тот же ракурс).

### Что не решено порогами
- `vehicle_proximity` даёт 3 ложных на роликах без нарушения (`pixabay-26239`, `mixkit-23378`): рамки человека и техники
  в кадре пересекаются при расстоянии ~3 м (глубины в 2D нет), оператор в кабине попадает внутрь рамки техники.
- `running` и `overcrowding` — см. таблицу; `immobile` — пропуски из-за коротких меток.
- Обучать/подбирать на 18 метках нельзя дальше: после утверждения разметки (K12) перебор повторить.

## Офлайн-оценка (P60)

```
py -m worker.main --offline --video ../demo/videos/x.mp4 --camera x --out runs/events.jsonl   # без бэкенда, CPU: --device cpu
py -m eval.evaluate runs/events.jsonl eval/labels.json --durations runs/events.durations.json
py -m eval.tune frames.json labels.json --max-false 0
```
- `--offline` читает файл целиком, без пропуска кадров; ts события = `--start` (по умолчанию `2000-01-01T00:00:00Z`)
  + кадр / FPS, часы компьютера не используются. Рядом с журналом пишется `*.durations.json`.
- Зоны ролика - `eval/zones/<файл>.json` (см. `zones/README.md`); без файла зонные правила молчат.
  Заглушки «зона на весь кадр» из K20 убраны, `eval.run report` берёт те же файлы по имени ролика.
- `eval.evaluate` по типам: найдено, пропущено, ложные, дубли (больше одного события на интервал метки),
  задержка (с, от начала метки до первого события: среднее и максимум) и ложные на час видео без меток.
- `eval.tune` выбирает минимум пропусков при ложных не больше `--max-false` (по умолчанию 0).
- Новых цифр по роликам нет: зон для роликов ещё никто не нарисовал, веса на этом диске не использовались.

## Устойчивость к условиям съёмки (P67, слайд 5: освещение, пыль, ночь)

Val набора СИЗ (`data/ppe`, 4509 кадров, тот же, что в обучении) прогнан через искажения, веса `ppe-v1`
(`runs/release-ppe/best.pt`), imgsz 640, GPU. Искажения (`eval/robustness.py`, без случайности, сид 0):
`dark` - гамма 2.5 и яркость x0.7 (ночь); `fog` - смесь со светло-серым, t=0.5 (туман, пыль); `motion_blur` - горизонтальное
ядро 15 пикселей; `noise` - гауссов шум, сигма 25; `jpeg20` - JPEG качества 20; `backlight` - яркое пятно сверху по
центру, остальное x0.6 (контровой свет). Искажённые копии - во временной `runs/robustness/` (вне git).
Класса `person` в разметке val нет (метрики его не содержат). Цифры - на искусственных искажениях открытого набора, не на съёмке с площадки.

py -m eval.robustness val      # из папки ml/, ~10 минут на RTX 5070; результат runs/robustness/result.json

## Мелкие объекты: каска в десятки пикселей (P68)

`eval/small_objects.py`. Кадры val с касками (800 из набора, равномерно) приводятся к холсту 640x640 и уменьшаются так, что
медианная каска кадра = 16, 24 или 32 px (sqrt площади bbox): камера «дальше» при том же размере кадра. Три способа:
`full640` - СИЗ-детектор на кадре (как на LinQ), `full960` - он же на imgsz 960 (только замер, LinQ остаётся 640),
`crops` - детектор людей (yolo11n, как в воркере, conf 0.3) -> вырезка человека (+10% полей) -> СИЗ-детектор на вырезке
(imgsz 640), боксы возвращаются в кадр, NMS по классам. Один и тот же счётчик mAP для всех способов, GPU RTX 5070,
кадр за кадром. Вырезка - чистые функции `person_crop`/`boxes_to_frame` (тест `tests/test_small_objects.py`).
Классы `respirator` и `cigarette` в кадрах с касками почти не размечены, поэтому в таблице только `helmet` и `head`;
общий mAP - среднее по ним.

```
py -m eval.small_objects --limit 800 --weights2 runs/release-ppe-s/best.pt   # из ml/, ~2.5 минуты; runs/small_objects/result.json
```

Выводы (слайд 5: масштаб):
- Модель держит каску от ~24 px (mAP50 0.80-0.81 на кадре 640); на 16 px падает до 0.69-0.70, `head` (голова без каски)
  страдает сильнее каски. Это граница дальности: каска меньше ~20 px в кадре 640 - ненадёжный сигнал.
- `full960` лучше всего: +0.04-0.10 mAP50 на 16-24 px (на 32 px почти без разницы), по времени +1-3 мс. Но LinQ остаётся
  на 640, поэтому это ориентир для камер, где мелкие каски критичны, а не рекомендация по умолчанию.
- «Люди -> вырезка -> СИЗ» в этой постановке проигрывает кадру целиком (mAP50 ниже на 0.08-0.15, mAP50-95 ближе) и в 2-3
  раза медленнее: детектор людей на 16-24 px теряет людей (вырезки нет - нет и каски), а добавленный второй проход не
  компенсирует. Выигрыш только по `head` на 16 px по mAP50-95 (0.386 против 0.319). Честная оговорка: холст маленький
  (640) и людей мало; на настоящем 1080p/4K кадре вырезка даёт то, что у full640 отнимает ресайз, этот замер её не проверял.
- v2 (YOLO11s) стабильно на 0.01-0.03 mAP50 лучше v1 при любом способе.

Рекомендация: оставить кадр целиком 640 (LinQ) и ppe-v2; для дальних камер - ставить камеру/зум так, чтобы каска была не
меньше ~24 px в кадре 640 (или считать камеры 1080p+ по двум половинам кадра), вырезку по людям в воркер не добавлять.
Проверку на реальном широком кадре (вырезка из 1080p) стоит сделать отдельно, если дальние камеры окажутся в демо.

## P70: падение с высокой камеры, рамка или поза

Набор Simuletic/CCTV_Incident_Dataset_Fall_Lying_Down_Detection (Hugging Face, CC BY 4.0): 111 синтетических кадров 1024x1024 с лежащими (рамка и 17 точек) и 10 стоящих как контроль. Скачиваются только метки в `ml/data/p70` (вне git). Запуск: `py -m eval.fall_pose`.

| способ | лежащих найдено | стоящих ложно |
|---|---|---|
| рамка w/h >= 0.7 (порог `lying_ratio` из K20) | 110 из 111 | 0 из 10 |
| поза: голова на уровне бёдер (наклон туловища < 30 град.) | 45 из 111 | 0 из 10 |

Поза с порогом 45 град. находит 90 из 111, 60 град. — больше, но порог тогда ловит и согнувшегося человека; единственный лежащий с вертикальной рамкой (laying22, w/h 0.66) по позе тоже не лежит (туловище вертикально в кадре). Вывод: на этом наборе рамка лучше, и поза не добавляет ни одного кадра к рамке (рамка или поза: 109 против 110 у рамки, из-за laying21 без точек).

Что сделано: `fall` получил необязательную проверку по ключевым точкам (`lying_by_pose`, параметры `pose_lying`, `pose_max_slope`), по умолчанию выключена: `rules.yaml` не менялся, K20-оценка прежняя (`eval.run report`: fall 17 найдено, 63 пропущено, 2 ложных, 0 дублей — как до P70). Включать `fall: {pose_lying: true}` имеет смысл, только если на реальных роликах с высокой камеры лежащий получает вертикальную рамку; тест на синтетических позах это проверяет. Без точек в детекции правило работает по рамке.
