# train/ — модель (ML-1)

Цель — детектор СИЗ для воркера. Классы — в `data.yaml`.

## Порядок
1. **T1, с первого часа.** Собрать датасет «каска / голова без каски» из открытых наборов, привести к формату YOLO в `ml/data/ppe/` (вне git) и запустить обучение. Пусть идёт, пока делается остальное.
2. **L1, пока идёт обучение.** Запустить готовую YOLO на LinQ и замерить FPS, см. `../export/README.md`.
3. **T3, T4.** Респиратор, затем курение (мелкий объект — бонус).

## Датасет
    python3 ml/train/prepare_data.py            # скачать и собрать в ml/data/ppe/ (вне git)
    python3 ml/train/prepare_data.py --mini     # полный train + valid-mini (3 картинки)
    python3 ml/train/prepare_data.py --limit 20 # 20 картинок на часть — для пробы

Если Hugging Face закрыт, скачать `train.zip` и `valid.zip` вручную по ссылке из таблицы ниже и
указать `--zips-dir <папка>`. Классы источника: `hardhat` → helmet=1, `no-hardhat` → head=2. Person в этом наборе отсутствует; классы person, respirator и cigarette требуют других данных.

Прямые ссылки без логина: [train.zip](https://huggingface.co/datasets/keremberke/hard-hat-detection/resolve/main/data/train.zip), [valid.zip](https://huggingface.co/datasets/keremberke/hard-hat-detection/resolve/main/data/valid.zip). `--limit` ограничивает конвертацию, архивы всё равно скачиваются полностью (около 779 и 225 МБ). `train-mini.zip` у источника отсутствует.

## Проба обучения (1 эпоха, 20 train + 20 val)
    python3 ml/train/prepare_data.py --limit 20
    ml/.venv/bin/python ml/train/train.py --epochs 1 --batch 4 --imgsz 320 --workers 0 --device cpu --name smoke

## Обучение
    ml/.venv/Scripts/python -m pip install -r ml/requirements.txt    # один раз (Mac/Linux: ml/.venv/bin/python)
    ml/.venv/Scripts/python ml/train/train.py --epochs 50

Для RTX 5070 укажите `--device 0`. Перед загрузкой модели скрипт печатает версию torch,
версию CUDA, имена доступных GPU; после обучения — mAP50 по каждому классу валидации.
Если CUDA недоступна, явный выбор GPU завершится понятной ошибкой с командой установки
torch cu128. Команду установки запускайте Python из того же виртуального окружения.

## Респираторы: PPED (S4)

[PPED авторов](https://zenodo.org/records/6551758), лицензия CC BY 4.0.
[Прямой ZIP без логина](https://zenodo.org/records/6551758/files/PPED_data.zip?download=1)
(3.8 ГБ). Источник содержит отдельные VOC-классы `Gas_Mask` и `Mask`:
в общий набор попадает только `Gas_Mask` → respirator=3. На проверенном снимке
`20211102_160406.jpg` — полумасочный респиратор с фильтром и ремнями.
Обычные медицинские маски `Mask` не конвертируются.

```bash
python3 ml/train/prepare_respirators.py --limit 3
ml/.venv/bin/python ml/train/train.py --epochs 1 --batch 4 --imgsz 320 --workers 0 --device 0 --name smoke-respirator
```

Скрипт сливает данные в `ml/data/ppe`, сохраняя существующие изображения касок/голов.
Изображения и метки PPED имеют префикс `pped_`. Повторный запуск добавляет/обновляет
выборку, но не удаляет ранее добавленные файлы. `--limit` — максимум положительных
изображений на каждую часть; без него собирается полный набор. Близкие кадры одной
минуты сохраняются в одной части по детерминированному хешу; это не гарантирует
разделение по человеку или сцене, поэтому для оценки обобщения нужен отдельный ролик.
Небольшая проба подтверждает работу пайплайна, а не качество детектора.

Без локального архива скрипт использует HTTP Range: скачивает оглавление, XML и только
выбранные изображения, не весь ZIP. Нужен сервер с поддержкой Range; Zenodo может
отвечать медленно. Для скачанного архива: `--source-zip <путь/PPED_data.zip>`.

Проверено 2026-10-22: `--limit 3` успешно добавил 3 train + 3 val PPED к
20 train + 20 val касок/голов. На RTX 5070 (`torch 2.14.1+cu130`) одна эпоха
завершилась успешно, всего 23 train + 23 val, ошибок разметки нет. Валидация
содержала 3 изображения и 5 объектов respirator.

| Прогон | mAP50 helmet | mAP50 head | mAP50 respirator | Назначение |
|---|---|---|---|---|
| smoke-respirator, YOLO11n, 1 эпоха, imgsz=320 | 0.0009 | 0.0014 | 0.0021 | Проверка конвейера, не оценка обученной модели |

Веса и логи: `ml/runs/smoke-respirator/` (вне git). Для рабочего детектора нужен
полный набор и полноценное обучение; перенос качества с постановочных PPED-кадров
на производственные камеры этой пробой не проверялся.

## Сигареты: CigDet (S7)

[CigDet автора Ali Khan](https://data.mendeley.com/datasets/6hyrr8typ7/1),
DOI 10.17632/6hyrr8typ7.1, CC BY 4.0. Набор содержит 557 изображений,
446 train и 111 test, с YOLO bbox именно сигарет (не людей и не облаков дыма).
[Публичный ZIP без логина](https://data.mendeley.com/public-files/datasets/6hyrr8typ7/files/24e3327e-155e-4565-ab44-8b45dc6445ee/file_downloaded)
(35 МБ); [прямое файловое хранилище](https://prod-dcd-datasets-public-files-eu-west-1.s3.eu-west-1.amazonaws.com/950cd489-55b8-4a8f-af72-a764146048bd).
Визуально проверен bbox `smoking_0003.jpg`: рамка охватывает сигарету в руке у лица.

```bash
python3 ml/train/prepare_cigarettes.py --limit 3
ml/.venv/bin/python ml/train/train.py --epochs 1 --batch 4 --imgsz 320 --workers 0 --device 0 --name smoke-cigarette
```

Конвертер переносит исходный класс 0 в cigarette=4, добавляет префикс `cigdet_`,
сохраняет имеющиеся каски, головы и респираторы. Исходные train/test используются
как train/val (test после этого не является независимой финальной оценкой).
Поддерживаются HTTP Range для небольшой выборки и `--source-zip <CigDet_dataset.zip>`
для локального архива. Без `--limit` добавляется весь CigDet. Повторный запуск не
дублирует изображения и не удаляет ранее добавленные файлы.

Порядок полной сборки: `prepare_data.py`, затем `prepare_respirators.py`, затем
`prepare_cigarettes.py`. Повторный запуск базового `prepare_data.py` очищает общий
каталог, поэтому после него оба дополнительных набора нужно добавить заново.

Проверено 2026-10-22: добавлены 3 CigDet train + 3 val к общему набору,
одна эпоха YOLO11n на RTX 5070 (`torch 2.14.1+cu130`, imgsz=320, batch=4)
завершилась успешно: 26 train + 26 val. Валидация cigarette: 3 изображения,
3 объекта. Веса и логи: `ml/runs/smoke-cigarette/` (вне git).

| Прогон | mAP50 helmet | mAP50 head | mAP50 respirator | mAP50 cigarette |
|---|---|---|---|---|
| smoke-cigarette, 1 эпоха, 26 train + 26 val | 0.0006 | 0.0017 | 0.0020 | 0.0000 |

## Статистика и полная сборка (S19)

```bash
python3 ml/train/prepare_data.py
python3 ml/train/prepare_respirators.py --download-workers 4
python3 ml/train/prepare_cigarettes.py --source-zip ml/data/_download/CigDet_dataset.zip
ml/.venv/bin/python ml/train/stats.py
```

Для полностью локальной сборки PPED: `--source-zip ml/data/_download/PPED_data.zip`.
Удалённый PPED поддерживает `--download-workers 1..16` (по умолчанию 4):
независимые HTTP Range-запросы, 3 попытки, таймаут 30 секунд, проверка CRC/размера
и атомарное сохранение каждого JPEG. Полный положительный поднабор PPED содержит
1546 изображений Gas_Mask, около 1.91 ГБ сжатых JPEG. Это весь поднабор класса,
а не ограниченная smoke-выборка; остальные PPED-классы не загружаются.

`stats.py` печатает все классы из `data.yaml`, включая отсутствующие. Объекты
считаются только из валидных строк: известный ID, пять полей, конечные координаты
в 0..1, положительный bbox внутри кадра (допуск округления 1e-6). Картинка с
несколькими объектами одного класса считается один раз в колонке картинок.
В частично битой метке валидные строки учитываются, а сама метка помечается битой.
Пустая метка — допустимый отрицательный пример, отсутствующая учитывается отдельно.
Битые/отсутствующие/сиротские метки дают код выхода 1. JPEG содержимое скрипт не
декодирует: колонка «битые» относится к меткам, не к файлам изображений.

Полная сборка проверена 2026-10-23, без `--limit`, в порядке
`prepare_data` → `prepare_respirators` → `prepare_cigarettes`.
Включены все 1546 размеченных кадров PPED Gas_Mask и все 557 кадров CigDet.
Итого 15338 train и 4509 val. Пустые метки — отрицательные примеры;
битых, отсутствующих и сиротских меток не найдено. Класс person в этих
источниках отсутствует; для людей используется готовый детектор.

При полной загрузке Zenodo отвечал HTTP 429; после добавления ограничения
частоты запросов полный PPED успешно собран с сохранением кеша. При 429 все потоки соблюдают общий
`Retry-After` (секунды или HTTP-date; при отсутствующем/некорректном значении
60 секунд). Максимум три попытки на запрос; после исчерпания загрузка завершается
ошибкой, ожидающие задачи отменяются. Повторный запуск использует сохранённые
JPEG. Рекомендуется 4 потока; повышать параллелизм при ограничении сервера не нужно.

После повторного 429 загрузчик дополнительно ограничивает все HTTP-запросы
общим скользящим окном **100 запросов за 60 секунд**. Любой 429 останавливает
все новые запросы минимум на 60 секунд, даже при Retry-After=0; более длинный
Retry-After соблюдается полностью. На JPEG используется один Range, включающий
локальный ZIP-заголовок и сжатые данные до следующей ZIP-записи; CRC и размер
проверяются после распаковки. Ограничение действует и на повторные запросы.

## Долгое обучение и продолжение (S20)

```bash
ml/.venv/bin/python ml/train/train.py --name ppe-full --device 0 --epochs 100 --patience 20
# Продолжить прерванный прогон из ml/runs/ppe-full/weights/last.pt:
ml/.venv/bin/python ml/train/train.py --name ppe-full --resume --device 0
# Или указать сохранённый checkpoint явно:
ml/.venv/bin/python ml/train/train.py --resume ml/runs/ppe-full/weights/last.pt --device 0
```

`--patience` — число эпох без улучшения для ранней остановки (по умолчанию 100,
0 отключает). `--resume` продолжает незавершённый checkpoint с состоянием
оптимизатора и номером эпохи; завершённые/очищенные веса для этого не подходят.
Для нового обучения на готовых весах используйте `--base`, без `--resume`.
Путь отсутствующего checkpoint проверяется до загрузки модели.

После обучения фактическая папка прогона содержит `metrics.json`:
общие `mAP50`, `mAP50-95` и `classes` с ID и обеими метриками каждого оценённого
класса. Если Ultralytics выбрал имя `ppe-full2`, JSON будет в этой папке.
Классы без валидационных объектов не выдаются за нулевые метрики; при отсутствии
результатов общие значения равны `null`. В консоль выводятся готовые строки
Markdown-таблицы «Прогон / Класс / mAP50 / mAP50-95» для переноса сюда.
Разбор аргументов и запись результатов проверены с подменой модели, без обучения.

IDs в `data.yaml` подтверждены: 1=helmet, 2=head, 3=respirator, 4=cigarette.
Класс 0=person присутствует в конфигурации, но объектов в наборе нет;
людей для воркера находит отдельный готовый детектор, наша модель не считается
обученной на person. Ошибочной перестановки целевых классов на выборке не найдено.

**Особенность PPED:** некоторые JPEG имеют EXIF Orientation=6. После учёта
EXIF рамки совпадают; на необработанных пикселях изображение и рамки кажутся
повёрнутыми относительно друг друга. На примере `pped_20220406_204536.jpg`
проверены реальный `cv2.imread` и `ultralytics.utils.patches.imread`: оба возвращают
правильно ориентированные 2560×1440 пикселей (высота×ширина). Для визуального
просмотра через Pillow нужен `ImageOps.exif_transpose`. При смене загрузчика
необходимо повторно проверить эту особенность, а не молча игнорировать EXIF.

**Неполная разметка и ограничения:** CigDet размечает сигарету, но не головы;
PPED добавляет только респираторы, но не головы и другие СИЗ. В наборе касок
встречаются маски/респираторы, не размеченные нашим классом 3. При совместном
обучении неотмеченные объекты становятся ложным фоном и могут снижать recall.
Респиратор на шее остаётся объектом класса 3, поэтому наличие респиратора
в кадре не доказывает правильность ношения. Выборка 40 кадров не исключает
других ошибок; результат полного обучения оценивать по каждому классу и на S14.

Блокирующих точных пересечений или неверных ID не обнаружено. **S11 разрешён**
как первый измеряемый прогон с перечисленными ограничениями, не как выпуск
готовой модели. Команда из корня репозитория:

```bash
ml/.venv/bin/python ml/train/train.py --name ppe-full-n-640 --device 0 --imgsz 640 --epochs 50 --batch 16 --patience 20
```

При OOM уменьшить batch до 8, затем 4; перед повтором проверить отсутствие
живого предыдущего процесса. Набор/split во время обучения не менять.

## Дообучение по решениям оператора
`py -m eval.feedback` (из `ml/`, бэкенд запущен) выгружает кадры подтверждённых и ложных инцидентов в `ml/data/feedback/` (YOLO: `images/`, `labels/`, `manifest.json`). Ложные — пустые метки (трудные негативы).

### Демо-дообучение на решениях оператора
Выгрузка `eval.feedback` хранит рамку человека с индексом типа нарушения, поэтому `train/feedback_finetune.py` сначала переразмечает кадры детекциями рабочих весов: подтверждённый инцидент — детекции как есть; ложный — те же детекции без класса-виновника внутри рамки человека (no_helmet → head, smoking → cigarette). Остальные типы (нет класса детектора) пропускаются, отчёт печатается. Затем смесь с исходным train (по умолчанию в 10 раз больше фидбэка, `--ratio`), дообучение от рабочих весов (`--epochs`, по умолчанию 3) в `ml/runs/feedback-*`, валидация на неизменном val, печать «было → стало» по классам (и `compare.json`).

```bash
# из ml/, после py -m eval.feedback
py -m train.feedback_finetune --weights runs/release-ppe/best.pt --epochs 3
```
Рабочие веса не меняются и в Release не попадают: новые веса лежат в `ml/runs/feedback-*/weights/best.pt`, в рабочие их переводит человек после сравнения.

Ограничения: кадры в бэкенде уменьшены и с нарисованной рамкой нарушения, детектор видит и рамку; разметка — самоподсказка рабочих весов (ошибки подтверждённых кадров не исправляются). Для настоящего цикла нужен чистый кадр без рамки в полном размере.

Прогон `ppe-full-s-640` (YOLO11s, imgsz 640, 50 эпох, patience 20): запущен 23.10 около 21:10, batch 16, workers по умолчанию, GPU RTX 5070 ~79% / 5.7 ГБ, ~1,5 мин на эпоху, окончен 22:25. Валидация best.pt: all mAP50 0.929 / mAP50-95 0.581 (helmet 0.942/0.558, head 0.932/0.640, respirator 0.980/0.663, cigarette 0.860/0.464). Лог — `ml/runs/ppe-full-s-640.log` (вне git).
