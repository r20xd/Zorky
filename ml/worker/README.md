# Воркер: правила нарушений

Правила — классы в `ml/worker/rules/`, по файлу на правило. Какие правила включены у камеры, решает `ml/worker/rules.yaml` (камера -> правила -> пороги/зоны). Нет камеры в `cameras` — берётся `default`; правило не перечислено — у камеры выключено.

## Что включено на контрольной точке

Включено (`rules.yaml`, default):
- `no_helmet`, `no_respirator`, `smoking`, `danger_zone`, `fall`, `immobile` — обязательное по ТЗ.
- `vehicle_proximity` — сближение с техникой; единственное поведенческое с цифрами на сцене с людьми и техникой (P69, синтетика склада, находит, но с ложными).
- `distress_signal` — обязательное по ТЗ: high, удержание 5 с; нужен `--pose-weights`, только синтетика.
- `fence_crossing` — подлезание под ограждение; 9 из 15 на синтетике (P69), меньше ложных, чем у бега и сближения.

Выключено (строки закомментированы в `rules.yaml`, код правил не тронут):
- `running` — настоящего бега в данных нет, K20: 0 из 3, на синтетике 70 ложных.
- `phone` — P30/K20: 1 из 2 на бытовых роликах, 0 из 2 после подбора.
- `overcrowding`, `lone_worker` — K20/P30: 0 найденных, ролики короче порога.
- `under_load`, `at_height`, `loitering` — только синтетика, роликов нет.
- `vehicle_in_zone`, `vehicle_collision` — оценки нет вообще, только тесты на синтетике.

Включить обратно: в `rules.yaml` убрать «# » перед строкой правила (или добавить её в `cameras: <камера>`).

## Как добавить правило
1. Файл `ml/worker/rules/<имя>.py`: класс от `Rule` (или `HeadRule` для проверок «у головы») с `name` (= `type` события из контракта) и `check(person, detections, zones) -> Verdict(active, zone_id)`, декоратор `@register`. Параметры из yaml приходят аргументами `__init__`.
2. Строка в `rules.yaml`: `default: {<имя>: {параметр: значение}}` или в `cameras: <камера>: ...`.

Файл подхватывается сам (`discover`), `main.py` и `pipeline.py` не меняются. Антидребезг (одно событие на эпизод) делает `Debouncer` по паре (трек, `name`). Новый `type` события должен быть в `contracts/events.schema.json` — это правит капитан.

## Падение и неподвижность (K9)

`fall` и `immobile` включены в default rules.yaml и передают severity=critical.
Используется геометрия bbox существующего трека человека; новая модель позы не
требуется. `fall` ищет переход от вертикального bbox (width/height <= 0.8) к
горизонтальному (>= 1.2), с увеличением отношения сторон минимум в 2 раза за
`transition_s` (по умолчанию 1 секунда). После перехода правило активно до
возврата в вертикальное положение: Debouncer выдаёт одно событие на эпизод,
а не повторяет его каждые несколько секунд лежания.

`immobile` консервативно означает **лежачий и неподвижный человек >= 10 секунд**.
Обычный стоящий или медленно идущий человек не считается критичным. Эта трактовка
выбрана, чтобы выполнить критерий «стоящий → 0» и не считать ожидание работника
происшествием. Человек, впервые увиденный уже лежащим, не порождает `fall`, но
после `duration_s` может породить `immobile`. Неподвижность — смещение центра от
фиксированного anchor не более `max_center_shift` (0.1) от наибольшей стороны
исходного bbox; накопленный дрейф сбрасывает отсчёт. Время берётся из pipeline.now,
не из FPS/числа кадров. Отсутствие трека более max_gap_s (2 секунды) очищает историю.

Пороги отношения сторон относятся к нормированным bbox; перспективу, ракурс и
соотношение сторон конкретной камеры нужно учитывать при настройке. Это эвристика,
не доказательство травмы: реальные производственные ролики проверяются в K20.

Пример параметров камеры:

```yaml
cameras:
  cam-1:
    fall: {upright_ratio: 0.8, lying_ratio: 1.2, min_ratio_change: 2, transition_s: 1, max_gap_s: 2}
    immobile: {duration_s: 10, lying_ratio: 1.2, max_center_shift: 0.1, max_gap_s: 2}
```

Для временных правил есть необязательный `on_frame(now)` один раз на кадр,
включая пустой. Старые правила продолжают использовать check() без изменений.
Verdict может передать severity; pipeline и make_event сохраняют её по контракту.

## Бег в зоне техники (K11)

Правило `running` включено в default и проверяет только зоны с контрактным
`kind: machinery` («техника»). Принадлежность зоне определяется точкой ног
человека; вне такой зоны история скорости сбрасывается и событие не создаётся.
В событии передаются `zone_id`, bbox человека и severity=low по реестру типов.

Скорость считается по перемещению центра трека за скользящее окно `window_s`
(по умолчанию 0.5 с), делится на среднюю высоту bbox человека и время между
кадрами. Порог `speed_threshold: 1.5` задан в **ростах человека в секунду**.
Для подавления одиночного дрожания bbox нужны минимум `min_samples: 3`
наблюдения на интервале не короче `min_span_s: 0.25` с. Время передаёт pipeline,
а не счётчик кадров: смена FPS не меняет единицы порога. Окончательное
подтверждение и одно событие на эпизод обеспечивает общий Debouncer.

Внутренний `Detection.frame_aspect` хранит ширина/высота кадра: parse_tracks
заполняет его по реальному кадру. Горизонтальное нормированное смещение
умножается на frame_aspect, чтобы расстояние и высота bbox имели одни единицы
на широких и квадратных кадрах. Старые конструкторы Detection совместимы:
значение по умолчанию 1 означает квадратный кадр. При синтетических тестах
широкого кадра необходимо задавать aspect явно.

История пропавшего трека удаляется через `max_gap_s: 2`, при смене зоны или
движении времени назад сбрасывается; повтор timestamp не добавляет отсчёт
скорости. Порог нужно подобрать по перспективе и роликам конкретной камеры
в K20: движение камеры, ошибки трекера и перспективные искажения могут
вызывать ложные оценки скорости, это не физическая скорость в метрах/секунду.

```yaml
cameras:
  cam-1:
    running:
      zone_kind: machinery
      speed_threshold: 1.5
      window_s: 0.5
      min_span_s: 0.25
      min_samples: 3
      max_gap_s: 2
```

## Сближение с техникой (K10)

Воркер ведёт треки людей и техники (классы COCO `car`, `bus`, `train`, `truck`;
погрузчика в COCO нет — класс `forklift` подхватится, когда он появится в модели:
добавить id в `COCO_TRACKED` в `pipeline.py`). Правило `vehicle_proximity` считает зазор
между рамками человека и техники (0 при пересечении) в **ростах человека** и срабатывает,
если зазор меньше порога `min_frames` кадров подряд. Порог строже (больше) у движущейся
техники: `gap_moving: 0.8` против `gap_static: 0.3`; движется — центр трека техники смещается
быстрее `move_speed` (0.15 размера техники в секунду). Трек техники без id считается стоящим.

В событии — рамка человека и severity=critical; bbox техники в контракте нет. Расстояние и
класс техники пишутся в лог `worker.vehicle_proximity` при срабатывании.

```yaml
cameras:
  cam-1:
    vehicle_proximity: {gap_static: 0.3, gap_moving: 0.8, move_speed: 0.15, min_frames: 5}
```

## Телефон у оборудования (P13)

Класс COCO `cell phone` (id 67) трекается вместе с людьми. Правило `phone` срабатывает, если
центр телефона `min_frames` кадров подряд лежит у головы или кисти человека: в верхней доле
`head_part` (0.5) рамки, по бокам шире рамки на `side_margin` (0.25 ширины). Позу не
используем — только рамки. `zone_kind: machinery` — только когда человек стоит в такой зоне;
без `zone_kind` — везде.

```yaml
cameras:
  cam-1:
    phone: {zone_kind: machinery, min_frames: 5}   # или phone: {} — везде
```

## Перелезание через ограждение (P12)

Правило `fence_crossing`: точка ног (середина нижней кромки рамки) `min_frames` кадров подряд
внутри зоны `kind: fence` или отрезок от прошлой точки ног до текущей пересёк границу зоны.
Одно событие на эпизод — общий антидребезг.

```yaml
cameras:
  cam-1:
    fence_crossing: {zone_kind: fence, min_frames: 3}
```

## Подлезание под груз (P27)

Правило `under_load`: точка ног в зоне `kind: under_load` и человек пригнулся: высота рамки меньше
`height_frac` (0.6) медианной высоты этого трека стоя или высота/ширина ниже `min_aspect` (1.0);
`min_frames` кадров подряд. Прошёл рядом или стоя через край зоны — события нет.

```yaml
cameras:
  cam-1:
    under_load: {zone_kind: under_load, height_frac: 0.6, min_aspect: 1.0, min_frames: 5}
```

## Камеры из бэкенда (P19)

```
WORKER_TOKEN=... py -m worker.main --cameras-from-backend --backend http://хост:8080 --model best.onnx --device linq
```

Вместо `--video` и `--camera`. При старте и раз в 30 с воркер делает `GET /api/cameras` с `WORKER_TOKEN` и для каждой камеры с `source` держит свой поток на общей модели: новая камера запускается, удалённая останавливается, сменившая `source` перезапускается. Камеры без `source` пропускаются (запись в stderr). Бэкенд недоступен — работа продолжается по последнему списку, повтор через 30 с. Адреса в логах и ошибках маскируются: `rtsp://***@хост/путь?***`. `--video` и `--images` работают как раньше.
## Источники видео (P48)

Из папки `ml/`; `--video` и `source` камеры из бэкенда понимают одно и то же:

```bash
python -m worker.main --video ../demo/videos/cam1.mp4 --camera cam-1        # файл
python -m worker.main --images ../demo/frames/cam-1 --camera cam-1          # папка кадров
python -m worker.main --video rtsp://user:pass@192.168.1.10/stream --camera cam-1   # RTSP
python -m worker.main --video http://<ip>:8080/video --camera cam-1         # телефон как IP-камера
python -m worker.main --video 0 --camera cam-1                              # веб-камера номер 0
```

Строка из одних цифр - номер устройства (`cv2.VideoCapture(0)`), остальное открывается как файл или адрес. Обрыв веб-камеры или потока - переподключение раз в несколько секунд.

## Камера из папки изображений (P14)

Из папки `ml/`, при запущенном бэкенде:

```bash
python -m worker.main --images ../demo/frames/cam-1 --camera cam-1 --fps 5 --ppe-weights runs/release-ppe/best.pt
# Две папки — две камеры, в одинаковом порядке; повтор по кругу:
python -m worker.main --images ../demo/frames/cam-1 --images ../demo/frames/cam-2 --camera cam-1 --camera cam-2 --fps 5 --loop
```

`--images` — альтернатива `--video`, `--fake` и `--cameras-from-backend`; смешивать их в одном запуске нельзя.
В каждой папке читаются только файлы `.jpg` и `.png` (регистр расширения не важен),
без вложенных папок. Порядок — лексикографический по имени: для числовых серий
используйте одинаковую длину, например `0001.jpg`, `0002.jpg`, `0010.jpg`.
Без `--loop` после последней картинки камера заканчивается, с ним повторяется
тот же список; frame_id при повторе продолжает увеличиваться. `--max-frames`
ограничивает число обработанных кадров каждой камеры, включая повторы.

Темп задаёт положительный конечный `--fps` (по умолчанию 10). Изображения не
пропускаются: время чтения, ожидания общей модели и инференса входит в интервал,
а если обработка медленнее, фактический FPS уменьшается, без ускоренного
«догоняющего» чтения. Временные правила используют реальное monotonic-время,
как при видео, а не EXIF/mtime файлов. Используются те же детекторы, треки,
события, снимки, превью и отправка метрик, что для видео.

Пустая/несуществующая папка отклоняется до загрузки модели. Повреждённый JPG/PNG
останавливает запуск с сообщением о конкретном файле и ненулевым кодом выхода;
ошибки потока камеры также передаются в основной поток при нескольких папках.

## Сигнал бедствия (distress_signal)
Нужна поза: `--pose-model yolo11n-pose.pt` или `pose.onnx` (старое имя `--pose-weights` работает). Позы считаются второй моделью и привязываются к треку по IoU рамок (>= 0.4).

- Модель грузится только если для камеры в `rules.yaml` включено правило по позе (`POSE_RULES` в `rules/base.py`, сейчас `distress_signal`). Нет такого правила — флаг игнорируется, второй модели нет, FPS не страдает.
- Время позы считается отдельно и пишется в лог метрик: `FPS …, инференс … мс (поза … мс)`; оно входит в `inference_ms`. Отдельного поля в контракте Metrics нет.
- LinQ: `.onnx` идёт через `make_session`, то есть поза — отдельная программа (`pose.onnx` из `python -m export.linq`, K14). Реальный прогон на ускорителе не проверен; если программа позы не соберётся, запускай позу на CPU: `.pt`/`.onnx` с `--device cpu` (людей и позу тогда тоже считает CPU). Веса не в git.

## Правило уровня зоны (P29)

Правило, которому нужны все люди и зоны кадра сразу (`lone_worker`, `overcrowding`), наследует `ZoneRule` из `rules/base.py` вместо `Rule`:

1. Файл в `rules/`, класс с `name` (= `type` события), `@register`, параметры из yaml — аргументы `__init__`.
2. `on_frame(now)` — время кадра (вызывается каждый кадр, в том числе пустой); историю по зонам храни сам.
3. `check_frame(people, zones) -> list[ZoneVerdict(zone, active)]` — ответ по каждой интересующей зоне; помощники `people_in_zone` (по точке ног) и `zone_bounds` в `rules/geometry.py`. Нужную длительность считает само правило.
4. Строка в `rules.yaml`, как у остальных.

`find_violations` ведёт антидребезг по паре (id зоны, `name`), а не по треку. Событие: `bbox` = границы полигона зоны, `zone_id`, без `track_id`. Пример — `rules/zone_people.py`.

- `lone_worker: {zone_kind: two_person, duration_s: 30}` — в зоне ровно один человек дольше `duration_s`.
- `overcrowding: {zone_kind: crowd_limit, max_people: 5, duration_s: 10}` — людей в зоне больше `max_people` дольше `duration_s`.

## loitering (P43)

- `loitering: {zone_kind: danger, dwell_s: 20.0}` — точка ног трека в зоне `danger` дольше `dwell_s`; одно событие на эпизод, отдельно от мгновенного `danger_zone`.

## at_height (P38)

- `at_height: {zone_kind: height, dwell_s: 3.0}` — точка ног трека в зоне `height` дольше `dwell_s`; одно событие на эпизод (общий антидребезг). Прошёл мимо или задел край на секунду — события нет.
- Правило **не видит страховочную привязь** и не проверяет, пристёгнут ли человек. Это напоминание мастеру: «человек на высоте — проверьте страховку».
